Your tests pass. Your app still breaks. Here’s why.

Bugs get past passing tests in a few predictable ways. Dittopath checks for each one.

1 · Messy data

Real data is messy.

Why tests miss it
Test data is tidy: every field filled in, every name short. Real accounts have blanks, accents, emoji and settings from years ago.
What Dittopath does
Replays every journey with your users’ real data, made anonymous but kept just as messy.

In June 2025, blank fields in real data crashed Google Cloud services for hours. The code had never run on data like that. Google Cloud

2 · Bad days

Nobody tests the bad days.

Why tests miss it
Tests assume the server always answers, quickly and correctly. Real servers fail, stall and sometimes send back nothing.
What Dittopath does
Replays every journey with errors, slow answers and empty results, and checks your app still shows something helpful instead of a blank page.

In a study of 48 serious failures in widely used systems, 92% started with an error the software noticed, then handled badly. Yuan et al., 2014

3 · Server changes

The server changed. The app didn’t.

Why tests miss it
App tests use a saved copy of what the server sends, so they keep passing after the server changes.
What Dittopath does
Notices when your server starts sending something new, replays every journey against it and tells you which ones break. If it can’t check something, it says so instead of showing a pass.

At Microsoft Azure, 21% of serious incidents caused by software bugs came from parts of the system disagreeing about what the data looks like. Liu et al., 2019

4 · Real browsers

Your users aren’t on a fresh copy of Chrome.

Why tests miss it
Tests run in one clean browser. Real people use iPhones, translate the page, come back with old saved data or leave a tab open through your release.
What Dittopath does
Replays each journey all of those ways.

  • Returning visitorA draft saved last month crashes the editor
  • Tab left openPassed across the release

Browser translation rewriting a page is a well-known cause of crashes in React, one of the most popular ways to build web apps. React issue #11538

5 · Feature switches

Not every change is a pull request.

Why tests miss it
Teams turn features on and off with switches, straight in production. No pull request means no tests run.
What Dittopath does
Checks your journeys with every switch your users actually see, and checks a switch before you turn it on for everyone.
Feature switchnew-invite-flowon for 10% of users
Turn on for everyone?Not yet: 1 journey breaks
  • Sign upPassed with it on
  • CheckoutPassed with it on
  • Invite a teammateThe Send button is hidden

In thousands of Google outage reports from 2010 to 2017, 31% were triggered by a settings change, not new code. The Site Reliability Workbook

6 · After release

Some breaks only show up after you ship.

Why tests miss it
Problems at your hosting company, payment provider or network never appear in a test.
What Dittopath does
Keeps watching the same journeys on real visits after every release, and tells you within minutes when fewer people finish one, even if no code changed.
Checkoutpeople who finished itlive

Fewer people are finishing CheckoutSince 14:02, payments fail at “Pay”. No code changed: your payment provider is returning errors.

In a study of serious Microsoft Teams incidents, 6 in 10 weren’t caused by a bug in the code or settings at all, but by infrastructure, deployments and outside services. Ghosh et al., 2022

What Dittopath doesn’t do. Keep your servers running, or test how they hold up under heavy traffic. Keep your uptime and load-testing tools for that.
